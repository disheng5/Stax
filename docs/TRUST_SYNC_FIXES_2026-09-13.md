# 可信记账与静默同步修复

基线：`fe6e7e0`。工作分支：`codex/trust-sync-fixes`。

本文保留该轮修复的范围与边界。文档核对日期：2026-09-13；后续位置维度与技巧轮换已另见 [实现说明](ANALYTICS_POSITION_TRENDS.md)。整体能力见 [README](../README.md)，通用发布步骤见 [部署指南](DEPLOY.md)。

本轮只修改、测试和提交本地代码，未部署云函数、未修改生产数据或数据库权限。开发环境仍直连生产；不要把本地检查通过等同于已上线或已完成真机验收。

## 已完成

- 已结算玩家撤销补买：保留确认的剩余积分，同事务重算买入额与盈亏；原流水保留，撤销以实际操作人、撤销时间单独呈现。
- 弱网队列：重放只删除已确认的操作，保留重放期间新增项；新队列按账号和房间隔离。旧版没有身份信息的队列保留原数据，仅在该房间有待处理项时提供确认恢复入口，不擅自跨账号重放。
- 个人统计：修复分页失败后重复计数、重新计入删除记录；统一排除本人隐藏、删除和本人已移出的旧记录。不按名称猜测哪些是测试记录。
- 赛季计算：并发计算有代次校验，较旧任务不能覆盖新任务；跨积分榜的 seasonId 请求在读取视图前拒绝。
- 详情页：房间与全部流水组成完整缓存，一次提交渲染。后台完整校准成功前不替换旧列表；失败保留旧快照并重试。缓存完全相同则不重绘。
- 全部流水：没有 80 条等展示上限。后台分页最多五路并发，全部读取和房间版本校验成功后提交；测试覆盖 45 条分页失败及 1001 条同时间戳记录。
- 预热：首页数据返回后低并发预热最近五场。缓存最多持久保存十二场完整房间，不是每场流水条数上限。
- 战绩与维度：完整记录在本地同步计算，列表、统计、趋势和维度一次更新，不再等待第二份云聚合结果覆盖页面。
- 同步恢复：当前可见首页、战绩、维度、我的订阅近期记录和本人资料变化；详情订阅房间和玩家资料；积分榜合并请求，基础信息与榜单一次呈现。断线静默重连及轮询，隐藏页关闭新增订阅。
- 分享：四个分享出口使用中性固定描述，不包含个人积分、胜率、人数、累计流水或自定义房间名称；指定包内静态品牌图，避免默认页面截图泄露。房间与积分榜邀请路径保留。
- 邀请入场：新用户在当前页填写昵称、选择头像和初始手数后直接加入；不强制转到“我的”。只查看不要求补资料；失败保留输入，重复点击去重。
- 表达：未知错误统一友好兜底；趋势札记只比较等长样本，不再根据积分断言打法水平或把历史极值写成近期波动。

## 结算后的派生统计

核心结算、流水与 `derivedPending/derivedVersion/derivedRetryAfter` 在同一事务写入。

新前端发送可选的 `deferDerived: true`，先显示已确认的结算结果，再发起独立的 `syncDerived: true` 云调用。该新入口校验调用者是当前记录参与者。不带新参数的旧前端保留等待派生处理的方式；原 mode 按载荷形状推断的兼容逻辑不变。

派生处理从原始记录重算个人统计，包含最大赢亏的下降修正，不做不可靠的重复累加；用户计算令牌防止旧响应覆盖新结果。相关榜单重算完成后，仅清除匹配来源版本的待处理标记。任何阶段失败都保留任务；同操作号重试不会新增结算流水。

`settleGame/config.json` 增加一分钟一次的补偿触发器，每轮最多处理一场待处理记录。正常更新不等定时器，定时器只补偿失败或进程中断。该补偿不是“自动修复玩家记错的剩余积分”，不修改原始账目。不会自动扫描并重写全部历史数据；历史上已经漂移、且没有待处理标记的数据需单独核对后重建。

## 发布前检查

1. 先运行 `npm run check`、`npm run lint`、`git diff --check`。`git diff fe6e7e0 -- cloudfunctions/` 只表示本轮开发差异；发布还须对照各函数实际部署基线，不能据此推定线上版本。
2. 确认索引支持本轮查询：transactions 的 gameId 过滤与 timestamp 降序、_id 降序组合；games 的 status、players.openid 过滤与 _id 排序；games 的 derivedPending 与 derivedRetryAfter 过滤；可见页的 players.openid 与 startedAt 排序。以云控制台查询计划/缺索引提示核实，不删除现有索引。
3. 单独确认部署范围。先部署 `calcSeasonScore`，再部署 `recordTransaction`、`getSeasonView`、`getMyAnalytics`、`settleGame`。上传整个函数目录，不能漏掉 derived-stats.js、config.json 或后续新增的 getMyAnalytics/trend-note.js。
4. 确认补偿触发器实际启用，检查 settleGame 超时配置能覆盖一次单房间派生计算。若只上传 index.js，补偿链路并不完整。禁止通过客户端伪造 Timer 事件作为验收方法。
5. 用已发布旧前端验证费用分摊、创建、加入、结算、结束后修改；检查 settledCount/checkedOutCount、rankings.winRate 等旧字段仍然正常。
6. 再上传新前端。每完成一项双机验收再进行下一项，不同时叠加新的产品改版。

## 双机与兼容验收

| 场景 | 通过标准 |
| --- | --- |
| 分享首页、战绩、房间、积分榜 | 卡片描述及图片不带个人或房间统计；邀请可打开原记录 |
| 新用户打开房间分享 | 可先查看；加入时原地补资料并继续；取消或失败不产生玩家/流水 |
| 详情首次与重复打开 | 首次完整内容一起出现；随后不先出现一段流水、再整页替换；相同数据不重绘 |
| 45 条、100 条以上流水 | 全部可见；第二页断网不把已有列表缩成二十条；恢复后完整校准 |
| A 补买/结算/修改，B 停留详情 | B 自动更新对应内容，账目和流水对应同一版本 |
| A 结束或修正，B 停留战绩/我的/积分榜 | 正常网络自动更新；断网恢复后追上最新状态，无整页加载动画 |
| A 改名换头像，B 停留旧记录或积分榜 | 资料更新，不回退成“玩家”；统计不因资料更新改变 |
| 撤销兼容调用的自动回归 | 剩余积分不变，买入及盈亏重新对应；原补买与撤销两条事实均保留。当前模板无可见撤销入口 |
| 派生失败后重试 | 核心结算不丢，待处理标记保留；后续完成，不重复计数；最大赢亏随修正重算 |

测试正式共享云环境时，只使用明确标记且经授权的测试记录，不修改真实朋友局来验证故障。

## 仍需明确的边界

- 未读取生产数据库安全规则，也未关闭旧客户端的集合直读权限。跨赛季接口越界和分享卡片泄露已修，但不能据此声称“底层隐私权限已全部闭合”；旧客户端直读依赖仍需独立迁移方案。其他成员资料的订阅也受实际 users 读取权限约束，不能以开放整份用户文档作为排障捷径。
- 近期记录订阅窗口是二十场，并非完整流水的上限。超出窗口的很老记录发生后台管理修改，不保证由此订阅立即触发；再次进入会按缓存有效期校准。正常结束后三小时修正与近期记录在本轮重点验收范围。
- 弱网或断网不可能保证瞬时最新。本实现保留完整旧内容、自动重试，并显式保留未确认写操作；不把缓存等同于已确认的新数据。
- 自动测试使用真实函数入口加内存数据库，以及页面方法级渲染断言；没有模拟云平台所有事务、权限和索引行为。
- 资料弹框通过 320/390/430/768px 浏览器布局检查，未发生容器横向溢出。这不是微信原生输入、头像授权、键盘避让或双机网络的真机验收。
- 尚未测量生产冷启动耗时、真机帧率或真实网络同步延迟，不提供未经测量的毫秒承诺。
